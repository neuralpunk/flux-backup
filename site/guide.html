User guide

Flux Backup keeps snapshots of your folders: complete pictures of how they were at a moment, on an external drive or an SSH server. It runs on a schedule, when a drive is plugged in, or when you ask. You can use the desktop app, the flux command, or both; they share the same profiles and see each other's backups.

Flux Backup 0.2 Desktop app and CLI

Installing #

Packages. Releases provide .deb (Debian, Ubuntu), .rpm (Fedora, openSUSE) and an AppImage. The deb and rpm packages install everything: the app (flux-backup), the command-line tool (flux), the system-backup helper and its polkit policy, man pages and shell completions.

The AppImage contains the app and flux, but not the system-backup helper: root can't run programs from inside an AppImage. Install a package if you need system backups.

From source. You need Rust 1.91 or newer. The app also needs Node.js 20+ and WebKitGTK 4.1 (Fedora: webkit2gtk4.1-devel libsoup3-devel; Debian/Ubuntu: libwebkit2gtk-4.1-dev libsoup-3.0-dev). 

packaging/prepare-dist.sh                  # flux, flux-helper, man pages, completions
(cd app && npm install && npm run tauri build -- --no-bundle)   # the desktop app (optional)
sudo PREFIX=/usr packaging/install.sh

At run time Flux uses ssh for SSH targets, rsync on the server for Mirror over SSH, fusermount3 for flux mount, secret-tool for the desktop keyring, and pkexec for system backups. Each is only needed for the feature that uses it.

Ideas in two minutes #

Profile
Says what to back up, where to, how, and when. You can have as many as you like (say, “Home folder” daily to a USB drive, and “Documents” hourly to a NAS).
Snapshot
One backup run. Every snapshot is complete: you never need an older one to restore from a newer one. Unchanged files cost almost nothing.
Engine
Decides how snapshots are stored: Mirror (plain folders) or Vault (deduplicated, compressed, encrypted).
Retention
Rules that decide which old snapshots are removed, like “keep 7 daily, 4 weekly, 12 monthly”. Named and pinned snapshots are kept.

Your first backup #

In the app

Click New backup in the sidebar. A short guide asks one question per step: what to back up (your home folder by default), where to keep it (a connected drive, a folder or an SSH server), how to protect it (plain, encrypted, or written by rsync or Borg), and when. Review your answers, click Create backup, then Back up now.

In a terminal 
flux profile create home --target /run/media/me/Backup --source ~
flux backup home
flux snapshots home

Everything else is one click away and has sensible defaults: each group of settings is a row showing its current value; click it to open just that group in a dialog, and Done to close it. Nothing is saved until you click Save. A row with a problem says so in red.

While you choose what to back up, Flux counts what it adds up to after the exclusions (“About 32 GiB in 51,900 files”) and warns if that's more than the free space where it would go. The first backup copies everything. Later ones only copy what changed, and take seconds.

Each backup in the sidebar shows where it goes and how it's doing (“Backed up 2 hours ago”, “Failed 2 days ago”). Right-click one, or use the ⋯ button next to Back up now, to back it up, open its snapshots, activity or settings, duplicate or export it, see its recovery guide, or delete it. Deleting a profile never deletes the backups it made: they stay where they are. The menu key or Shift+F10 opens the same menu from the keyboard.

Mirror or Vault? #

MirrorVault
Stored asplain folders, one per snapshotpacks of chunks
Open without Fluxyes, with any file managerno (use Flux, or flux mount)
Unchanged fileshard links (no extra space)stored once across all snapshots, files and computers
Renamed or moved filescopied againnot stored again
Compressionnozstd
Encryptionuse an encrypted drive (LUKS)built in (XChaCha20-Poly1305, Argon2id)
SSH servers needrsynconly SFTP

Pick Mirror when you want to reach your files in an emergency with nothing but a file manager. Pick Vault for untrusted places (a friend's server, a drive that might be lost), for many similar machines sharing one target, or to save space.

The choice is per profile and can't be changed later; make a new profile instead.

Backups that don't need Flux #

Mirror and Vault are Flux's own formats. If you'd rather your backups never depend on Flux, choose compatibility mode: a standard, free tool writes them in its own format, and Flux is only the app you use. In the profile, click Choose… next to Usable without Flux, or use --engine rsync / --engine borg.

rsyncBorg
Stored asplain folders written by rsync, one per snapshota standard Borg 1.x repository, one archive per snapshot
Without Fluxany file manager, cp, rsyncborg list, borg mount, borg extract
Unchanged datahard linksdeduplicated chunks
Compression / encryptionno / use an encrypted drivezstd / repokey-blake2 with a passphrase
Needsrsync 3.1+ (and on the server)borg 1.2–1.4, package borgbackup (and on the server)

You don't need to know rsync or Borg. Next to your backups Flux keeps a recovery kit: FLUX-RECOVERY.txt, a plain-text guide written for this profile that starts with the basics (where your files are, what to copy and paste) and ends with a reference for experts, and flux-backup.sh, which runs the same backup with the tool alone. In the app, open it from Overview → Usable without Flux → Recovery guide, copy any section, or save a copy to a USB stick. In a terminal: 

flux recovery home                   # print the guide
flux recovery home --script          # print the backup script
flux recovery home --save /run/media/me/USB

Everything else works as with the other engines: browsing, restores (symlink-safe, keeping your files), retention with pins and names, schedules, checks and flux mount. The full user guide has the exact layout and commands for rsync and Borg users.

A Borg passphrase can't be recovered. Keep it safe, and keep a copy of the key too: the recovery guide has the borg key export command for your repository.

Where backups go #

An external drive

When you pick a drive in the app (or create a profile pointing at a mounted drive), Flux remembers the drive's filesystem UUID. If that drive isn't connected, Flux refuses to write into the empty mount point, so it never fills your system disk by mistake.

Backups go into a flux-backup/ folder on the drive (Mirror) or flux-vault/ (Vault).

An SSH server

flux profile create docs --target me@nas:/srv/backup --source ~/Documents --engine vault
flux ssh test docs          # can we log in, write, and (for Mirror) run rsync?

Flux uses your system's ssh, so ~/.ssh/config, agents and hardware keys all work. Scheduled backups can't type passwords or accept new host keys. Set up a key once, and point the profile at it with target.identity_file = "~/.ssh/flux_backup_ed25519" (or in the app's Where to keep it › Connection details): 

flux ssh keygen             # creates ~/.ssh/flux_backup_ed25519 (no passphrase, for timers)
flux ssh copy-id docs       # installs it on the profile's server (asks for your password once)

Mirror over SSH needs rsync on the server and keeps hard-linked snapshots there. Vault over SSH only needs SFTP; the server never sees your data unencrypted. target.bandwidth_limit (e.g. "5MB") caps the upload rate.

Choosing what to back up #

sources.paths lists files and folders. Exclusions use gitignore syntax, matched against absolute paths:

PatternMatches
*.tmpany file ending in .tmp, anywhere
node_modules/every folder named node_modules
~/Videosthat folder only
**/target/debug/target/debug at any depth
!keep.tmpre-includes something an earlier pattern excluded

Also available:

  • skip folders with a CACHEDIR.TAG (on by default);
  • skip folders that contain a marker file (exclude_if_present = [".nobackup"]);
  • skip big files (exclude_larger_than = "4GB");
  • stay on one filesystem (one_file_system).

In the app, What to back up › Leave some things out suggests common exclusions (caches, trash, build output) with how much space each takes in your sources.

Automatic backups #

Schedules are systemd timers, so backups run even when the app is closed. The timer is created when you save a profile with a schedule (or with flux schedule install <id>).

SettingExampleMeaning
trigger = "calendar" on_calendar = "daily", "Mon..Fri 18:00", "*-*-* 03:30" at those times; with catch_up, a time missed while the computer was off runs at the next start
trigger = "interval" every = "4h" when the last successful backup is older than that
on_connect = true also when the profile's drive is plugged in
skip_on_battery = true scheduled runs wait for mains power
skip_on_metered = true scheduled runs to a server wait while the connection is metered (mobile data, a phone's hotspot, as NetworkManager reports it) 
flux schedule status        # every profile's timer and next run
flux schedule sync          # make timers match all profiles
flux schedule remove home

Scheduled backups run at low CPU and I/O priority (options.nice, options.io_priority), keep the computer from suspending while they run, and notify you if something went wrong (and, if you turn it on in Preferences, when they succeed).

Pausing. For a presentation, a slow connection or a full disk: Pause all scheduled backups… in any backup's menu, in Preferences, or in the tray, for an hour, until tomorrow morning (7:00) or until you resume them. The sidebar shows they're paused, with Resume. Backups that come due meanwhile are skipped, not queued; backing up by hand still works. 

flux pause --for 2h      # or --tomorrow, or nothing: until `flux resume`
flux resume

Upkeep. In Settings › More schedule options, a backup can verify every stored byte once a month after a scheduled backup ([maintenance] verify_monthly = true); you're notified if anything is wrong. Vault backups also free the space of removed snapshots once a week (free_space_weekly, on by default): each backup only marks old snapshots as removed, and this deletes the data only they used. Results appear in the run's log in Activity.

Preferences (bottom of the sidebar) also hold: start in the tray when you log in, the theme, and the exclusions new backups start with.

Getting files back #

In the app

Open Snapshots, pick a snapshot from the list, browse to what you need, select it, and Restore. You can restore:

  • into another folder: the safest choice; nothing on your computer changes;
  • back to where it was: identical files are skipped. Different files are kept as name.flux-<snapshot> unless you choose to replace them.

Before you restore, the dialog shows what would happen: how many items are added, which files differ from what's there now (and whether they'd be kept or replaced), and how many are already identical. Replacing files needs the red Restore and replace button.

What changed shows the differences from the previous snapshot; the ⋯ menu also compares with the files on disk now.

To just look at a file, double-click it (or right-click › Open a copy). Flux restores a read-only copy into a temporary folder and opens it with your usual app; nothing on your computer changes. Save it somewhere else if you want to keep it, or restore it. Temporary copies are removed after a day.

Don't know which snapshot? Type part of the name in Find in all snapshots (above the snapshot list) and press Enter. Every file or folder with that in its name is listed, from all snapshots; files you've since deleted are marked Deleted with the last snapshot that had them. Click one to show it in its snapshot. * works as a wildcard (*.pdf), and a / matches whole paths (Documents/*.odt). flux find matches the same way.

Versions of a file. Right-click a file › Versions of this file… (or select it and click Versions) lists each different version with its date and size, and which snapshots hold it. Open one to look at it, or restore it.

The first search of a Vault, Borg, rsync or SSH backup reads every snapshot's listing; Flux keeps an index of them in its cache folder (readable only by you), so later searches and Versions are quick. Plain folders on a drive need none.

In a terminal

flux ls home                                   # the newest snapshot's top level
flux ls home ~/Documents --snapshot 2026-11-01  # a folder in the snapshot of that day
flux find home report                          # search all snapshots (part of a name)
flux find home '*.odt'                         # or a pattern
flux history home ~/notes.md                   # every version of one file
flux diff home --live                          # what changed since the newest snapshot
flux restore home ~/Documents/report.odt --to ~/Restored
flux restore home ~/Documents                   # back in place (asks first)

Snapshots are chosen by id, by a unique start of an id, by name, or as latest. Mirror ids are start times (2026-11-01_03-00-00), so 2026-11-01 picks that day's snapshot when there is one.

As folders: flux mount

mkdir ~/snapshots
flux mount home ~/snapshots
ls ~/snapshots/latest/home/me/

Every snapshot appears as a read-only folder named after its start time, plus a latest link. This works for every engine, including Vaults and backups on SSH servers, so you can open old files with any program or compare folders with your usual tools. Press Ctrl+C (or run fusermount3 -u ~/snapshots) to unmount. --snapshot <spec> shows just one snapshot at the mount point.

What to keep #

[retention]
keep_last = 1          # always keep the newest N
keep_within = "1day"   # keep everything from the last day
keep_hourly = 24
keep_daily = 7
keep_weekly = 4
keep_monthly = 12
keep_yearly = 5
max_age = "10y"        # remove anything older, whatever the buckets say
keep_named = true      # named and pinned snapshots are never removed
min_free_space = "50GB"          # remove oldest snapshots until this much is free
min_free_inodes_percent = 5

Each bucket keeps the newest snapshot of each of its last N hours, days, weeks, months or years. Pruning runs after every backup. Run it yourself with a preview: 

flux prune home --dry-run

In the app (What to keep › Keep and remove snapshots), the retention editor shows which of your current snapshots each rule would keep or remove, and why.

To keep a snapshot forever, pin it (flux pin home <snapshot>). To mark one, name it (flux name home <snapshot> before-upgrade). By default, named snapshots are kept too.

Vault passwords #

An encrypted Vault needs its password to back up, browse or restore. Where it comes from is set per profile:

vault.password_sourceUse
{ from = "keyring" }the desktop keyring (default): asked once, then remembered
{ from = "prompt" }asked every time; scheduled backups can't run
{ from = "file", path = "…" }first line of a file (make it mode 0600)
{ from = "command", command = "pass show backup" }first line printed by a command

FLUX_PASSWORD overrides all of them, for scripts.

The password is chosen when you set the backup up, not at its first run. In the app, choosing an encrypted format in a new backup (or turning on Encrypt with a password in its Settings) asks for it twice right there; when you click Create backup, Flux creates the encrypted Vault (or Borg repository) with it and keeps it in the keyring (or writes it to the key file, if that file doesn't exist yet). So the first backup, even a scheduled one at night, has nothing to ask. A backup that was set up before this, or whose drive wasn't connected at the time, shows the same fields in its Settings until its first backup. On the command line, flux key init <profile> does the same.

A Vault can have several passwords. Each one opens it, and changing them never re-encrypts data:

flux key list docs
flux key add docs --label "spare, in the safe"
flux key passwd docs
flux key remove docs <key-id>

There is no way to recover a Vault whose passwords are all lost. Keep a second password somewhere safe.

Checking your backups #

flux check home              # structure: every snapshot complete, every file accounted for
flux check home --read-data  # also read and verify every byte (slow)

The app has the same under Maintenance on a profile's overview. Vault data is authenticated, so any corruption or tampering is detected.

System backups #

To back up things only root can read (/etc, /root, other users' files), use system profiles. They live in /etc/flux-backup/ and run from system timers, even when nobody is logged in.

In the app

Click System backups at the bottom of the sidebar. Flux explains what it needs; then your desktop asks for an administrator password. System profiles then appear and work like your own. The app locks them again after 15 minutes without use, or when you click the lock.

In a terminal: add --system and run as root 
sudo flux --system profile create etc --target /run/media/me/Backup -s /etc -s /root
sudo flux --system backup etc

Some differences from your own profiles:

  • An encrypted system Vault can't use the desktop keyring. The first time you unlock it in the app, tick Keep it for scheduled backups: the password is saved in /etc/flux-backup/keys/<id>, which only root can read.
  • Hooks of system profiles run as root.
  • Restoring as root never follows a symbolic link someone else planted on the way to the destination. If a folder on the path is a link owned by another user, the restore stops and says so; restore into another folder instead. When root restores into a folder that belongs to someone else, setuid bits are dropped and device files are skipped.

Hooks #

Commands to run around a backup:

[hooks]
pre_backup  = ["mount /mnt/nas"]          # a failure cancels the backup
post_backup = ["notify-send 'Backup done' \"$FLUX_SNAPSHOT_ID\""]
on_error    = ["logger -t flux \"$FLUX_ERROR\""]
timeout = "10m"

They run with sh -c and get FLUX_EVENT, FLUX_PROFILE, FLUX_PROFILE_NAME, FLUX_ENGINE, FLUX_SOURCES, FLUX_TARGET, FLUX_TRIGGER, FLUX_STATUS, FLUX_SNAPSHOT_ID, FLUX_SNAPSHOT_PATH and FLUX_ERROR. Their output goes into the run's log.

Keeping an eye on things #

flux status            # what's running, last result and next run of every profile
flux watch home        # live progress of a running backup
flux cancel home       # stop it; the next run continues where it stopped
flux log home          # recent runs
flux log home --run last   # everything that happened in one run, including warnings

The app shows the same: a coloured dot per profile, live progress for every backup however it was started, and an Activity tab with the full log of each run.

Fine Some files couldn't be read Failed Running

Problems in Activity shows only the runs that failed or skipped files.

The Overview tells you in words when something needs you: the drive hasn't been connected for a while, the last few backups failed, no backup has succeeded for longer than its schedule suggests (3 days for a daily backup, 30 for a manual one), or the destination is almost full.

Space. For a backup on a drive, the Overview shows how full the drive has been over the last weeks and, once there are a few backups to go on, when it fills up at that rate (“full in about 3 months”), with the projection dashed on the chart. Hover the chart or use the arrow keys for exact values, or open Show as a table. Under a month left, it's also a warning at the top. Steady use (old snapshots removed as fast as new ones are added) says so.

To set up a similar backup (the same folders to a second drive, say), use Duplicate in the backup's menu or flux profile duplicate home: the copy is called “… (copy)” and opens in Settings.

Asking for help. Copy diagnostics (in Activity) or flux diagnostics home gives a report to paste into a bug report: versions, the profile with password commands and hooks hidden, and the latest runs and their messages.

An interrupted backup (power cut, Ctrl+C, unplugged drive) doesn't damage anything. The unfinished snapshot is never shown, and the next run continues it.

Exporting and importing profiles #

A profile can be exported, to keep a copy, set up another computer, or take the same backup to another tool: as a Flux profile (importable again), a borgmatic configuration, or a restic, rsync or Borg script. Whatever a format can't express (pins and names, the schedule, free-space floors…) is listed in the export dialog and as comments in the file.

In the app: right-click a backup › Export…. To import: + next to Your backups › Import a profile…. 

flux profile export home -f borgmatic -o ~/
flux profile import home.flux-profile.toml

Profile reference #

Profiles are TOML files in ~/.config/flux-backup/profiles/<id>.toml (system profiles: /etc/flux-backup/profiles/). Edit them in the app, with flux profile edit <id> (opens $EDITOR and validates the result), or by hand. Unknown keys are errors, so typos don't go unnoticed.

home.toml 
version = 1
name = "Home folder"
engine = "mirror"                 # or "vault"

[target]                          # a local folder or drive…
kind = "local"
path = "/run/media/me/Backup"
fs_uuid = "3f1c…"                 # refuse to write unless this filesystem is mounted there

# [target]                        # …or an SSH server
# kind = "ssh"
# host = "nas.local"
# user = "me"
# port = 22
# path = "/srv/backup"
# identity_file = "~/.ssh/flux_backup_ed25519"
# ssh_options = ["Compression=no"]
# bandwidth_limit = "5MB"

[sources]
paths = ["/home/me"]
exclude = ["~/.cache/", "node_modules/", "*.tmp"]
exclude_larger_than = "8GB"
exclude_caches = true
exclude_if_present = [".nobackup"]
one_file_system = false

[retention]                       # see "What to keep"
enabled = true
keep_last = 1
keep_within = "1day"
keep_daily = 7
keep_weekly = 4
keep_monthly = 12
keep_yearly = 5
keep_named = true

[schedule]                        # see "Automatic backups"
trigger = "calendar"              # "manual", "calendar" or "interval"
on_calendar = "daily"
catch_up = true
skip_on_battery = false
skip_on_metered = false           # backups to a server wait on metered connections
on_connect = false

[maintenance]                     # upkeep after scheduled backups
verify_monthly = false            # read every stored byte back about once a month
free_space_weekly = true          # Vault: delete data no snapshot uses about once a week

[options]
preserve_acl = true
preserve_xattr = true
symlinks = "preserve"             # "preserve", "follow_unsafe" (copy targets outside the sources), "follow"
change_detection = "metadata"     # or "checksum": also compare contents (slow)
continue_on_errors = true         # finish even if some files can't be read
snapshot_if_unchanged = false
nice = 10
io_priority = "best_effort_low"   # "normal", "best_effort_low", "idle"
notify = true
backup_before_restore = true      # keep files that a restore would replace
threads = 0                       # 0 = automatic

[vault]                           # Vault profiles only
compression_level = 3             # 0 (off) to 22
encryption = true                 # fixed when the Vault is created
password_source = { from = "keyring" }

[hooks]                           # see "Hooks"

Durations are written like 90s, 15min, 4h, 1day, 2weeks; sizes like 500MB or 4GiB.

Troubleshooting #

“the drive with filesystem UUID … is not mounted at …” / “backup target … does not exist”

The profile's drive isn't connected or mounted. Connect it; with on_connect, the backup then starts by itself.

A scheduled backup didn't run

Check flux schedule status and flux log <id>. Scheduled runs skip on battery when skip_on_battery is set, and can't ask for a Vault password or accept a new SSH host key. Run flux backup <id> once in a terminal to see the problem.

“Permission denied” for some files

They're listed in the run's log, and the snapshot is marked completed with problems. Exclude them, or back them up with a system profile.

SSH: “Host key verification failed” or a password prompt

Run flux ssh test <id> in a terminal once to accept the host key, and flux ssh copy-id <id> to install a key.

flux mount: “cannot mount”

Install fuse3 (it provides fusermount3), and mount on an empty folder you own.

Where is everything?

flux config path prints the folders Flux uses.

Something missing or unclear? Every command also has a man page, like man flux-restore.
